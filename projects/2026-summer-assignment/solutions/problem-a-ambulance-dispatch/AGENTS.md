# A题论文 AI 协作约定

## 人与 AI 的职责

- 协作者使用自然语言表达意图，不要求背固定口令或手工执行 Git 命令。AI必须识别“查看变化、准备编辑、完成检查、提交修改”四类语义，而不是只匹配某个句子。
- AI 负责同步、建分支、编辑、验证、差异报告、Commit、Push 和创建 PR。
- AI 不得自动合并 PR。最终 Merge 必须由仓库负责人在阅读差异和验证结果后确认。
- 遇到合并冲突、数值/公式/引用变化、权限不足或无法验证时停止，不得猜测处理；向协作者和负责人报告。

## 分支职责

- `main` 是唯一长期分支，由论文负责人直接维护，承载已发布版本和正在开发的新版本。
- 论文是否正式发布由 `paper/vX.Y/` 版本目录、README发行说明和版本Tag表示，不再用长期开发分支区分。
- 协作者只提交校对意见时不创建分支；需要直接修改正文时，从最新 `origin/main` 创建 `review/<姓名或代号>-<主题>` 短期分支。
- 协作者 PR 的目标分支必须是 `main`。AI只负责创建PR和增删报告，不得自动Merge。
- PR经论文负责人审核合并后，短期 `review/*` 分支可以删除；仓库不维护 `develop`、`feature` 等其他长期分支。

## 唯一正文源

- 当前唯一允许手工编辑的论文源文件是 `paper/v2.5/A题论文(v2.5).md`。
- 该 Markdown 同时是 GitHub、VS Code 和后续 DOCX 转换的唯一内容基准；仓库不再维护单独的 GitHub 预览版。
- 正文修改必须先停在 Markdown 审核门：向论文负责人提交内容增删报告；只有负责人明确回复 Markdown 内容通过后，才能生成或覆盖 DOCX。
- DOCX 阶段只实现已审核正文的 Word 原生公式、分页和版式，不得借排版之机修改正文、数字、公式、引用或结论。若排版时发现内容问题，退回 Markdown 修订并重新审核。
- DOCX 由论文负责人统一生成和排版。除非任务明确授权，不得修改或覆盖 DOCX、转换清单、冻结结果、图表或代码。

## AI 必须执行的工作流

1. 读取根目录 `AGENTS.md`、本文件和项目 `README.md`。
2. 检查 `git status`。发现与本任务无关的未提交改动时保留，不得暂存、回退或覆盖。
3. 获取远程更新。工作区允许安全切换时，从最新 `origin/main` 创建短期分支；分支名使用 `review/<姓名或代号>-<主题>`。
4. 修改前记录目标章节和修改边界。默认只编辑唯一 Markdown 正文源；不得改变任务范围外的数字、单位、公式、模型定义、引用和结论。
5. 修改后用 VS Code 自带预览和 GitHub 实际渲染语法检查显示效果，并运行与改动风险相称的测试。
6. 输出“内容增删报告”，至少包括：基准提交、修改文件、逐节新增、逐节删除/替换、数字/公式/引用是否变化、验证结果、未解决问题。
7. 正文有变更时，在生成 DOCX 前等待论文负责人明确确认 Markdown 内容；未确认时只交付唯一 Markdown 正文源和内容增删报告。
8. 只暂存本任务文件，使用清晰 Commit 信息；不得使用全量暂存夹带其他改动。
9. Push 当前工作分支并创建指向 `main` 的 PR。PR 正文必须包含内容增删报告和验证结果。
10. 把 PR 链接交给协作者和仓库负责人；不得自动 Merge 或删除分支。

## 入口一：查看 main 新变化

当协作者要求查看最新版或比较变化时，AI必须：

1. 只执行 `git fetch origin` 获取远程信息，不先覆盖协作者工作区。
2. 找到当前分支与 `origin/main` 的共同基准提交。
3. 分开报告两类差异：`origin/main` 相对共同基准的新增变化；当前本地分支相对共同基准的个人变化。不得把两类变化混成一份报告。
4. 重点比较当前正式论文的唯一 Markdown 正文源；同时说明 main 是否发布了新的论文版本目录。
5. 按章节说明 main 新增、删除、改写了什么，并单列数字、公式、模型、引用和结论变化。
6. 默认只报告，不修改、合并、暂存或提交任何文件。只有协作者明确要求开始修改时，才进入入口二。

## 差异报告策略

- 报告的第一任务是解释“这个版本为什么值得发布、读者实际获得了什么”，不是复述 Git 行差异。先通读全部差异并提炼一条版本主线，再选择支持该主线的证据。
- 开头用一段“版本定位”回答：本次是模型/结果升级、论证补强、写作重构、排版发布，还是混合升级；说明最重要的收益及是否改变结论。
- 使用 `[+]`、`[-]`、`[~]`：`[+]` 表示新增完整能力/论证模块，`[-]` 表示整体移除的内容，`[~]` 表示已有内容发生实质调整。禁止使用大面积 `diff` 代码块。
- 以“语义改动单元”而不是“Git 行”为粒度。同一目的、同一结果的多处改动必须合并为一条。例如三个任务各新增算法表，应合并为“新增三问统一的算法设计层”，并在括号中说明覆盖内容，不得拆成多个机械加号。
- 每条先写变化结论，再解释价值或影响；不得只罗列操作步骤。无独立价值的步骤列表应压缩为一个上位概念。
- 按重要性排序，而不是按文件或章节顺序：结论/模型/结果变化 > 论证与可复现性 > 结构与表达 > 纯排版和编号。
- 标题编号、表号顺延、标点、同义改写、引用显示格式等，除非影响阅读、转换或合规，否则合并为一条“次要编辑”，不进入核心变化。
- 完全未改变的内容集中写成一句“未变项”。不要为了证明未变而逐个重述数值、模型或章节。
- 数字、公式、模型、引用或结论发生变化时必须逐项列出；若没有变化，只写一句明确结论。
- 报告长度由实质变化决定，通常保留2至6条核心变化。宁可少而准确，不得为了形式完整填充低价值条目。
- PR 的 `Files changed` 是完整逐行差异的权威入口；报告负责解释重点、影响和风险，不替代原始 diff。

## 入口二：修改论文并提交 PR

当协作者给出内容修改任务时，AI必须先完成入口一的比较，然后：

1. 在不丢失本地工作且无未解决冲突的前提下，使工作分支基于最新 `origin/main`；必要时创建 `review/<姓名或代号>-<主题>` 分支。
2. 只编辑当前正式版本的唯一 Markdown 正文源。
3. 用 VS Code 自带预览检查显示效果；Push 后再以 GitHub 页面为在线显示依据。
4. 提交 Markdown 内容增删报告并等待负责人确认；需要 DOCX 时，确认后再由论文负责人生成和排版。
5. 完成当前获准阶段的验证、Commit、Push 和 PR，然后停止等待负责人审核。

## 语义入口：准备编辑

当协作者表达“准备自己修改论文”的意图时，AI必须把它解释为“协作者自己编辑，AI只准备安全工作区”。触发表达包括但不限于“我要修改论文”“我要改论文”“我自己改一下”“帮我开个修改分支”“准备修改正文”。AI自动执行：

1. 读取根目录和本项目的 `AGENTS.md`，检查 `git status`，不得覆盖、暂存或回退任何已有修改。
2. 执行 `git fetch origin` 获取最新远程信息。
3. 只有在工作区允许安全切换时，基于最新 `origin/main` 创建并切换到 `review/<协作者代号>-edit`；若不知道代号，使用 GitHub 用户名或当前 `git user.name` 生成简短代号。
4. 若存在未提交修改、未解决冲突或目标分支已存在且状态不明，停止并说明情况，不得强行切换、stash 或覆盖。
5. 打开当前版本唯一正文 `paper/vX.Y/A题论文(vX.Y).md`，不修改正文、不暂存、不提交、不Push、不创建PR。
6. 明确回复当前分支名、正文路径和“现在可以开始修改；完成后告诉我‘修改完成’”。

## 语义入口：完成检查

当协作者表示已经改完、但没有明确要求提交时，进入“完成检查”。触发表达包括但不限于“修改完成”“我改好了”“检查一下我的修改”“看看我改得怎么样”。AI必须：

1. 确认当前位于为本次修改建立的 `review/*` 分支；若不是，停止并报告。
2. 检查完整差异和 VS Code/GitHub 兼容显示，确认只修改了获准范围内的唯一 Markdown 正文源。
3. 输出内容增删报告，单列数字、公式、模型、引用和结论变化以及未解决问题。
4. 先向协作者展示报告并等待明确确认；此时不得暂存、Commit、Push 或创建 PR。
5. 只有协作者明确确认提交后，才只暂存本任务文件，完成验证、Commit、Push，并创建指向 `main` 的 PR；不得自动 Merge。

## 语义入口：提交修改

当协作者明确表达“把当前论文修改提交到仓库并交负责人审核”的意图时，进入“提交修改”。触发表达包括但不限于“提交论文”“提交修改”“把论文交上去”“帮我提交 PR”“改好了，发 PR”“推送并提交审核”。AI必须：

1. 结合当前仓库、分支和对话理解“提交论文”是 Git 协作提交；若用户可能指竞赛平台正式交卷，必须先澄清，绝不能上传到竞赛平台。
2. 确认当前位于 `review/*` 分支，并检查完整差异、修改范围、显示效果和远程 `main` 新变化。
3. 生成内容增删报告，单列数字、公式、模型、引用、结论以及未解决问题。
4. “提交论文”等表达本身视为对 Commit、Push 和创建 PR 的明确授权，不再机械要求用户重复一句确认。
5. 只有在改动范围清楚、无未解决冲突、无无关文件夹带且验证通过时，才只暂存本任务文件，Commit、Push，并创建指向 `main` 的 PR。
6. 若存在语义冲突、数字/公式/模型/引用/结论口径冲突、验证失败或夹带文件，停止并展示报告，等待人工决定。
7. 创建 PR 后停止并返回 PR 链接；不得自动 Merge 或删除分支。

## 意图判定优先级

- 以整句话和当前上下文判断意图，不区分是否使用完全相同的关键词。
- 明确的“提交、推送、发 PR、交审核”优先于普通的“改好了”，进入“提交修改”。
- 只有“改好了、修改完成”而没有提交含义时，进入“完成检查”，不 Commit、不 Push。
- 只有“我要改、准备编辑、开分支”时，进入“准备编辑”，AI不得代写或提交。
- 含义仍不清楚时只问一个简短问题，不得自行扩大到提交、Merge 或竞赛平台交卷。

## 冲突处理

- AI 可以先获取并分析最新 `main`，但不得在语义冲突时自行选择一边。
- 同一段文字冲突时，列出“当前分支版本、main 版本、建议整合稿”，等待人确认。
- 数值、参数、公式、指标口径、引用或结论冲突必须由负责人决定。
- DOCX 冲突不做自动拼接；以 Markdown 内容源和负责人保留的人工排版版为准重建。

## 每次交付给人的固定摘要

```text
分支：
基准提交：
版本定位（一段话）：
核心变化（按重要性列出2至6条，使用 [+] / [-] / [~]）：
数字/公式/模型/引用/结论变化：
未变项（一句话）：
次要编辑（可省略）：
验证：
PR：
需要人工决定：无 / 有（逐项列出）
```
