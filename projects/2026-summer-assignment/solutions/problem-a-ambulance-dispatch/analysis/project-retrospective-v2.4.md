## 3. 最终问题理解与模型合同

### 3.1 题目数据能力

原题提供 10 个需求区域的中心坐标、面积、人口、日均呼叫量和距最近医院距离，以及 6 个候选站点的坐标、停车容量和建设信息；没有逐条呼叫时间戳、逐小时频数、道路网络、真实响应记录或伤情等级。

因此必须区分：

- 区域中心是聚合需求的代表点，不表示现实呼叫都发生在中心；面积可用于需求密度与代理局限讨论，但不能恢复区内呼叫空间分布。
- 任务二的日内峰谷是合成情景，不是历史拟合；必须写清这一证据边界。
- “距最近医院距离”不影响任务一站点到呼叫点的出车距离优化；它只适合补充说明后续转运链条。
- 题目给出的 45 min 是车辆一次任务的平均占用周期；不能再重复叠加为 45 min 加准备、行驶、处置和返程。

### 3.2 任务一：容量约束运输规划

最终逻辑是“先由容量证明配置唯一，再优化长期服务分流”，但论文中不把必要性证明写成一页代数推导。

1. 枚举启用 1—6 个站点时的最大配车数：3、5、7、9、11、12 辆；对应日运力 36、60、84、108、132、144 次。
2. 前五种均小于 140 次/日，只有六站全建可行。因此六站全部启用，唯一配车为 `(3,2,2,2,1,2)`。
3. 固定配车后，用连续流量 `x_ij` 表示区域 `i` 的长期日均需求中由站点 `j` 承担的次数；连续值是长期平均，不是“半次呼叫”。
4. 第一层最小化加权出车距离，第二层只在距离最优解集合内提高 3 km 规划服务覆盖，采用词典序而非任意加权和。
5. 最优平均出车距离为 0.941569 km，3 km 规划服务覆盖率为 86.429%，仅忽略容量时的潜在 3 km 覆盖率为 97.143%；需求残差与容量超限均为 0。

最终论文的重点不是“所有站点全建”的长证明，而是可执行的容量约束运输分配及其距离、覆盖结果。完整分配用水平堆叠条形图呈现，避免一张大表与一张热力图重复表达同一信息。

### 3.3 任务二：给定日总量的条件 NHPP 与连续多日离散事件仿真

最终到达模型为：每天固定 140 次呼叫，按周期双高斯密度随机化 24 h 内的到达时刻，再按区域日均量比例标记区域。这是“给定日总量后的 NHPP 条件到达时刻分布”，不能同时声称每日总量仍服从 Poisson。

仿真合同：

- 30 天预热，30 天统计；最终 30 个独立复制，种子为 400000—400029。
- 车辆忙闲、FCFS 队列和未完成任务跨午夜继承；00:00 只重置新的日接单计数。
- 最后统计日 24:00 停止生成新呼叫，但已到达呼叫继续排队、派车和完成，直至系统排空。
- 单车每天最多接受 12 次任务；12 辆车固定归属六站，任务完成后回原站。

三种策略：

- A：全局就近派车基准。
- B：45 min 前瞻的覆盖保护与日负荷联合派车，最终参数为 `beta=4`、`delta=2`；作为日常主策略。
- C：S3 固定 1 辆备用车、等待超过 7 min 时解除保护；这是独立的显式备用配置，不与 B 混成同一策略。

30 个样本外复制的平均响应时间分别为 5.6142、5.3432、5.5872 min。B 较 A 的成对差为 -0.2711 min，95% CI 为 `[-0.3116,-0.2305]`；B 的 P95 为 9.9006 min，日均延迟成本减少 7089.22 元。C 用于满足“给出备用车辆配置”的题意，但不替代性能更好的日常主策略 B。

### 3.4 任务三：连续事故时长下的应急响应

事故区总强度设为常态的 5 倍，即在常态呼叫流上叠加 4 倍增量。事故持续时间 `H` 是 `[0.5,12] h` 上的连续变量；不能把六个初始仿真点误写成离散的全部可能时长。

实现采用：

- 初始节点 0.5、1、2、4、8、12 h；自适应补充到 10 个节点（最终含 5、6、10、11 h）。
- 最不利起点按 1 min 网格计算周期强度积分。
- 常态预测 `B_N` 与事故感知预测 `B_E` 使用共同随机数；`B_E` 只在事故识别后修正未来 45 min 的需求预测，不增加车辆。
- 逐复制构造 PCHIP 响应面，再跨复制形成 95% 置信带；PCHIP 只是有限节点间的数值近似，不是精确连续解。

随 `H` 从 0.5 h 增至 12 h，`B_N` 下全市平均响应时间从 6.1706 min 增至 31.6386 min。全市层面的 `B_E-B_N` 在 10 个节点均不显著；事故区在 8、10、11 h 分别改善 0.1519、0.0941、0.1965 min。结论必须限定为：在本文固定车队和 5 倍事故强度设定下，容量约束的影响大于预测修正的边际作用。不能泛化为“应急策略普遍无效”。

## 4. 决策时间线与关键转折

### 4.1 题意与模型阶段

1. 用户要求从零开始，不使用旧分析结果，并要求每问先给互斥方案再选择。
2. 任务一先确认六站容量总和恰好 12 辆，但用户指出仅做容量算术证明过于草率，要求建立含需求守恒、站点服务能力、站点车辆上限和总车数的运输型规划。
3. 队友论文审查暴露三类口径混用：实际运输覆盖、仅判断附近是否有站点的潜在覆盖、含准备时间的严格诊断覆盖。最终保留可执行运输分配，并修正完整分配矩阵。
4. 任务二围绕“保护性派车 B 是否等同备用配置”反复讨论，最终明确 B 是派车规则，C 是独立显式备用配置。
5. 跨午夜任务、最后统计日排空、30 天预热、双高斯条件 NHPP 逐项冻结。
6. 用户指出随机生成细节被过度展开，要求把终点重新放回“给出可解释调度方案与平均响应时间”。
7. 任务三曾被错误改成若干离散时长；用户提醒此前已确认连续函数，触发返工，最终改为自适应节点加 PCHIP 连续响应面。

### 4.2 实现与论文阶段

1. 代码曾花数小时研究预热参数 `w`，且出现“先说 40 天、后变 3 天”的口径漂移。最终由用户直接冻结 30 天，证明该参数没有必要占据主要研究资源。
2. 早期仿真平均响应约 30 min，与队友约 5 min 相差过大；用户要求回到题面重新确认，最终发现需要固定每日 140 次，而不是让无条件 NHPP 随机日总量叠加造成超负荷。
3. 用户多次补充静态 3 km 与动态总响应 4 min 的解释、医院距离、区域中心、面积和 200 元/(min·次) 延迟成本。说明数据字典与指标口径应在编码前一次性冻结。
4. v2.1—v2.3 主要在仓库清理、字体、行距、对齐、版本目录和发布规范上迭代；v2.4 才系统修正标题层级、引文上标、算法设计、学术措辞、公式、三线表和数据图。
5. 最终 Git 工作流改为中文 README 默认、英文 README 保留、发行说明精确到分钟并标记 UTC+8、每版存于 `paper/vX.Y/`、新版本 Word 挂到 Release、提交使用用户 GitHub 身份。

## 5. 踩坑清单、根因与防复发规则

### 5.1 未先完成模型合同就开始写作

**表现**：静态覆盖半径、准备时间、每日呼叫数、连续事故时长和策略边界尚未统一，便开始运行长仿真和拟写论文，导致后续多轮返工。

**根因**：没有持久化、可签字的决策日志；聊天中的“选择1”未被转换为带语义的冻结记录，长上下文压缩后容易丢失。

**规则**：题面事实、缺失数据、每问结论类型、模型合同、待确认项全部进入新项目初始化的 `state/decision_log.json` 或项目决策表。冻结项被改动时必须写“旧值—新值—原因—影响范围”，未经确认不得擅自更改。

### 5.2 本末倒置：把随机参数与实现细节当成研究终点

**表现**：为确定预热 `w` 花费数小时；反复讨论随机时刻如何生成，而主问题只是调度方案、备用配置与平均响应时间。

**根因**：没有“决策价值”门槛和计算预算；实现细节一旦可研究，就被无限扩展。

**规则**：参数研究必须回答“它是否可能改变方案选择或结论”。若否，采用文献/诊断支持的保守固定值并做一次简短稳定性检查。预实验默认 10—20 min 时间盒；超时仍不影响核心决策时立即冻结，不写进正文主线。

### 5.3 验证过度，尤其是文件哈希

**表现**：不改文件内容的重命名仍多次比较哈希；临时渲染和未后处理文件清理做了多轮路径、哈希和备份检查；外部 XSD 校验超时拖慢发布。

**根因**：没有按风险分层；把高风险模型结论、低风险文件移动和可再生 QA 产物使用了同样强度的验证。

**规则**：

- 内容未变的移动/重命名：一次 Git 状态检查和一次结构验证即可。
- 内容或模型改变：运行受影响测试与复现。
- 最终冻结发布：只在此时计算一次三件套哈希并交给独立终审。
- 可再生渲染图/PDF不做持久备份；Git 已跟踪产物以提交为回退点。
- 外部网络校验设 60—120 s 上限，已有充分本地证据时记录超时，不重复等待半小时。

### 5.4 任务一证明过长

**表现**：早期用一页以上代数推导证明六站全建，挤占服务分配与结果解释的篇幅。

**根因**：把“严谨”等同于“展开所有简单算术”。

**规则**：简单容量必要性用一段文字加一张紧凑运力表。独立显示公式只保留模型定义、目标、约束和非平凡统计量；`140/12`、`121/140` 等纯数值计算写入正文或表格。

### 5.5 格式规范未前置

**表现**：早期稿件不是宋体、字号偏小、一级标题不居中/编号不规范、正文被误居中、行距过大/过小/不统一、标题断行、引用未上标。

**根因**：先写内容、后凭印象套模板；只检查样式名，没有检查 Word 的直接格式、文档网格和最终渲染。

**规则**：写正文前先从用户样例和官方规范抽取“排版合同”，编码为后处理规则和回归测试。样式检查必须覆盖段落、表格、OMML 和实际页面渲染。

### 5.6 三线表名义正确、视觉错误

**表现**：表级 OOXML 已设置顶线、表头线、底线，但每行 `tblPrEx` 残留粗边框，渲染成“逐行粗横线表”；另有表格列宽过窄、孤字换行和同列对齐不统一。

**根因**：只检查表级边框，没有检查行级例外和渲染结果；表宽按平均分配，未根据字段语义设计。

**规则**：

- 三线表只保留表级顶/底线和表头下线；清除行级 `tblPrEx` 边框、左右边线与内部网格。
- 顶/底线 `w:sz=10`，表头线 `w:sz=4`，明确形成粗细层级。
- 表格 10 pt、1.15 倍行距；短字段和数值优先单行，先调列宽和单元格边距，再考虑缩字。
- 算法设计表表头居中，正文两列左对齐；普通结果表逐列统一对齐。
- 手工 WPS 修改若应永久保留，必须同步回后处理脚本和测试，否则下一次重建会覆盖。

### 5.7 公式与引文排版异常

**表现**：显示公式靠左；`d_ij`、`i=1` 等复合下标在 Word 中竖排；响应时间公式部分内容“消失”；`mod`、`exp[ ]` 写法不标准；正文 `[1]—[4]` 不是上标；GitHub 把 `D^*` 的星号当 Markdown 强调符号。

**根因**：Markdown—Pandoc—OMML—LibreOffice 链路中只验证了源 LaTeX，没有检查转换后的 OMML run；文献引用与数学上下标被混为同一问题。

**规则**：

- 所有显示公式段居中，使用原生 OMML。
- 同级复合下标作为一个 OMML run，例如 `ij`、`i=1`，不得拆为连续嵌套脚本。
- Markdown 中用 `D^{\ast}` 规避裸 `^*` 被抢先解析。
- 余数运算用 `%`，指数函数写为 `\exp(\cdot)` 或 `e^{\cdot}`；先在数学上标准，再考虑转换兼容。
- 正文文献序号单独拆 run 并设上标；参考文献表编号保持常规基线。
- 纯数字算式不独立占行；行内公式也要检查是否完整可见。

### 5.8 图表重复、信息密度低

**表现**：分配矩阵表与热力图重复；“相对 A 的平均响应差”图只有一个指标；表11/12一度被拆成大量小图；任务三两条曲线完全重合却未解释。

**根因**：先按数据列画图，没有先定义论点和证据链。

**规则**：每幅图先写一句“这张图必须证明什么”。同一数据不重复做表和图；精确数字多、便于查值时用表，结构/比较/趋势更重要时用图。多指标策略对比可做一张有主次层级的多面板大图；复杂的节点数值和置信区间保留表。曲线重合不是绘图错误时，直接解释效应小于图尺度，并用成对差与置信区间图揭示细微差异。

### 5.9 边改边审、过早启动独立 review

**表现**：用户仍在逐项给出表格、图和公式修改时就多次启动终审；冻结哈希不断漂移，审查代理读到旧文件或“未后处理”中间文件。

**根因**：没有清楚区分内容冻结、版式冻结和发布冻结。

**规则**：用户明确“可以终审”或变更清单全部关闭后才启动一次最终 W2。终审输入只使用精确正式路径，不用 glob；`paper/vX.Y/` 只保留三件套，任何中间文件移出该目录。审查后产物有实质变化，旧 PASS 自动失效。

### 5.10 仓库清理与 `git clean` 事故

**表现**：曾使用 `git clean -X -e backups/`，误以为 `-e` 是“从删除集合排除”；实际它把目录追加为忽略规则，反而纳入 `-X` 的删除集合。`-n` 已预告 `Would remove backups/`，仍继续执行，造成未跟踪本地资料删除风险。

**根因**：误解命令语义，并在 dry-run 明确显示危险目标后没有停止。

**规则**：不再使用 `git clean -X -e` 做混合清理。跟踪文件用 `git rm`，未跟踪文件用显式、精确、已核对的路径；dry-run 出现任何计划外目标立即停止。用户/其他任务的 `shared/` 文件永不依赖模糊排除规则保护。

### 5.11 一开始缺少关键 Skill

**表现**：早期缺少端到端总控、论文手、摘要、科研可视化和成熟 DOCX 规则，导致模型决策没有持久化、摘要未二次验证、图表先画后想、Word 靠反复目测修正。

**根因**：把“有一个数模 Skill”误认为覆盖题意、代码、写作、可视化和 Office 的全部环节。

**规则**：下次启动即加载最小完整栈：`mathmodel-skill` 总控决策日志，`建模手`，`编程手`，`论文手`，摘要 Skill，科研可视化 Skill，DOCX 工具。按阶段懒加载，不一次性读无关材料；关键门禁由未参与编写的质检者执行。

## 6. 哪些做法值得保留

- 用户坚持“从零开始”和“先给选项再决定”，有效阻止了直接复制队友论文错误。
- 用容量约束运输模型替代纯最近站分配，修复了站点超载与分配不可复现问题。
- 把 B 保护性派车与 C 固定备用明确分开，兼顾了性能与题目对备用配置的显式要求。
- 条件化每日 140 次呼叫，消除了题意与无条件 NHPP 随机总量的冲突。
- 共同随机数、成对置信区间和样本外复制使策略比较有统计证据，而不是看单次随机结果。
- 任务三用自适应节点与逐复制 PCHIP 保留连续时长设定，同时避免连续区间逐点仿真的不可能要求。
- 版本目录、双语 README、精确发布时间、用户署名提交和 Release 附件形成了可持续发布流程。
- 把最终用户发现的格式问题写进代码与测试，而不是只在 WPS 中临时修，最终解决了“改完又反弹”。

## 7. 下次任务的协作协议

### 7.1 用户如何发布指令

推荐在第一条指令中一次性交代：

1. 任务类型与目标：竞赛/作业、题号、截止时间、默认交付 Word 或 LaTeX。
2. 权威输入：题面、附件、官方规范、优秀样例；旧论文只作待审材料，不是默认正确答案。
3. 协作方式：每问先给 2—3 个互斥的高层方案，说明推荐、代价和与其他问的边界；一次只确认一个真正会改变模型的决策。
4. 决策权：已冻结结论不得擅自改变；若实现发现冲突，先报告“证据—影响—备选”，再等待确认。
5. 时间与深度：参数扫描、搜索和终审的时间预算；是否接受情景假设、是否需要灵敏度分析。
6. 排版与发布：指定参考 Word、版本号规则、GitHub 仓库、是否允许直接 push/Release、提交署名。

可直接复制的启动指令见 `templates/personal-modeling-playbook.md`。

### 7.2 助手应如何完成

1. 读取题面和全部附件，列数据字段、单位、缺失项、可用性和每问必须回答的结论类型。
2. 建立决策日志；把用户的“选1”记录为有语义的 D 编号，不依赖聊天位置。
3. 完成 M1 后才编码；先做最小纵向切片 P1，再全量运行和正式出图，P2 后才写论文。
4. 对随机仿真设计算预算；任何长计算前报告“目的、预计时长、停止条件、会改变什么决策”。
5. 写论文前建立 Claim—Evidence 表：每个摘要数值、正文主张、图、表、公式、代码输出都有精确落点。
6. 先冻结内容，再做 Word；手工排版变更同步进脚本和测试。
7. 用户逐项审阅阶段不启动终审；变更清单关闭后，做一次 W2 冻结终审。
8. 发布时只做一次最终哈希、一次暂存范围审查、一次提交和一次远端核对；中间不重复备份可再生产物。
9. 上下文压缩后读取决策日志和当前状态；摘要中的旧用户消息是历史，不是新指令。

## 9. 一句话结论

这次项目的主要损耗不是模型太难，而是“模型合同、实现预算、论文格式与发布流程”没有在开始时同时冻结。下次应把这些内容都视为模型的一部分：先理解和签字，再实现和验证，最后一次性写作、排版、终审与发布。
