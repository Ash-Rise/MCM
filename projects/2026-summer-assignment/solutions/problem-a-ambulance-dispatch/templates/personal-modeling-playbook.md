# 个性化数模工作流与论文模板 v1.1

> 适用范围：中文数学建模课程作业、校赛、CUMCM 类竞赛。官方当届规范永远优先；本文是无冲突时的默认协作与版式基线。

## 1. 一键启动指令模板

```text
使用 mathmodel-skill 总控，并调用建模手、编程手、论文手、摘要、科研制图和 DOCX 工具完成本题。

任务信息：
- 类型/题号：<课程作业或竞赛、题号>
- 截止时间：<时间>
- 权威题面与附件：<路径>
- 官方格式/参考样例：<路径>
- 交付物：默认 Word；是否需要代码、结果表、图、Release：<说明>
- Git 仓库与版本：<仓库、版本号、是否允许直接 push>

协作要求：
1. 从原题和原始数据开始；旧论文/旧代码只作待审材料，不直接继承结论。
2. 每个子问先给 2—3 个互斥的高层方案，说明推荐、代价、风险和与其他子问的边界；一次只让我决定一个关键分岔。
3. 把每次选择写入持久化决策日志。冻结结论未经我确认不得更改；实现发现冲突时先报告证据与影响。
4. 先完成题意、数据、指标、假设和模型合同，再编码；真实结果冻结后才写论文。
5. 长计算前说明目的、预计时长、停止条件和它可能改变的决策。与主结论无关的参数研究限时 20 分钟。
6. 内容修改全部完成后再做一次独立终审，不要边改边审。
7. Word 必须遵守下方个性化排版规范；手工修改必须同步到生成脚本和测试。
8. 过程中持续工作，状态汇报不结束任务；上下文压缩后从决策日志恢复，不把旧消息视为新指令。
```

## 2. 十一阶段工作流与硬门禁

| 阶段 | 核心产物 | 进入下一阶段的条件 |
|---|---|---|
| 0 启动 | 截止时间、交付物、仓库、权威输入清单 | 输入与目标明确 |
| 1 题面取证 | 子问、数据字段、单位、缺失项、歧义表 | 用户确认关键歧义 |
| 2 方案比较 | 每问 2—3 个模型候选与反例 | 选定模型族 |
| 3 模型合同 | 假设、符号、目标、约束、输入输出、验证、失败条件 | M1 PASS |
| 4 最小实现 | 一条从输入到关键结果的最小链 | P1 PASS |
| 5 全量实现 | 正式实验、结果表、复现清单 | 数值与约束冻结 |
| 6 图表设计 | 图表契约、候选图、灰度/尺寸 QA | P2 PASS |
| 7 证据大纲 | Claim—Evidence 映射、论文大纲、摘要事实表 | W1 PASS |
| 8 写作与内容审核 | Pandoc源、内容增删报告 | 用户明确确认Markdown内容 |
| 9 Word 装配 | 按已审核正文生成DOCX、转换清单、逐页渲染 | 确定性门禁通过 |
| 10 终审发布 | W2、版本日志、Git 提交、Release | 冻结快照 PASS |

硬规则：

- 不在题意/数据/指标未冻结时开始全量计算。
- 不在真实结果未冻结时写摘要与结论。
- Markdown是内容审核门。正文修改后先更新Pandoc源；未收到用户明确确认，不生成或覆盖DOCX。
- DOCX阶段只处理Word原生公式、分页和版式，不修改已审核正文。排版暴露内容问题时，退回Markdown修订并重新审核。
- 不在用户仍逐项修改时启动最终终审。
- 不因“更复杂”自动认为“更好”；每问最多两个独立模型体系。
- 不为可再生中间文件做多轮备份或哈希审计。

## 3. 决策日志模板

每个关键决定使用以下格式，写入新项目初始化的 `state/decision_log.json` 或 `analysis/decision-log.md`：

```text
D-<编号> <主题>
状态：候选 / 已冻结 / 被替换
题目证据：<原题字段或条款>
选择：<完整语义，不写单独的“1”>
放弃方案：<方案及原因>
实现影响：<代码、参数、结果、论文哪些部分受影响>
验证方式：<约束、对比、统计或文献>
变更记录：<时间、旧值 -> 新值、用户确认>
```

当用户说“选择1”时，助手必须立即回写为语义完整的决定，例如“D-07：任务二采用给定每日总量的条件 NHPP”，而不是只记数字。

## 4. 计算预算模板

长计算启动前必须给出：

```text
目的：该计算要区分哪些方案或验证哪条主张？
最小试跑：<规模、预计用时>
全量规模：<复制数/网格/数据量、预计用时>
停止条件：<误差、稳定性、时间上限>
决策价值：结果不同会改变什么？结果相同将冻结什么？
```

默认预算：

- 环境/最小纵向切片：5 min 内。
- 非核心参数筛选：10—20 min；超时后选保守固定值并记录依据。
- 正式随机实验：先 3 个复制筛选，再 30 个样本外复制；具体数量服从问题精度需求。
- 文件哈希：只在最终冻结/发布时一次性计算。
- 渲染：开发阶段抽查受影响页，最终阶段才逐页检查。

## 5. 论文内容大纲

### 首页与摘要

1. 题名：一句话包含“对象 + 核心约束/方法 + 目标”，优先单行。
2. 摘要总起：对象、规模、总模型路线。
3. 逐问各一段：问题 → 具体方法 → 带单位数值 → 验证/结论。
4. 收束：适用边界或最重要的因果限定。
5. 关键词：3—6 个，与正文术语一致。

摘要不放显示公式；所有数字必须有正文/结果文件出处。定稿前按“结构扫描 → 逐问找结果 → 找模型名 → 找创新 → 找验证”二次检查。

### 正文默认结构

```text
一、问题重述
二、问题分析
  2.1 任务一分析
  2.2 任务二分析
  ...
三、模型假设
四、符号说明
五、任务一：<方法或目标>
  5.1 数据/指标定义
  5.2 模型建立
  5.3 算法设计（三线表）
  5.4 结果与解释
  5.5 验证/小结
六、任务二：...
七、任务三：...
八、模型评价
参考文献
附录（只放复现入口、必要补充，不堆工程日志）
```

每个任务遵循相同证据闭环：

- 该问要回答什么；
- 为什么选这个模型；
- 变量、目标、约束和输入输出；
- 算法如何执行；
- 关键数值结果与单位；
- 结果是否显著/可行/稳健；
- 适用边界与不能推出的结论。

## 6. Word 排版基线

精确机器配置见 `personal-paper-profile.yaml`。默认视觉规范：

| 元素 | 默认格式 |
|---|---|
| 页面 | A4，四边 2.5 cm |
| 题名 | 宋体、15 pt、加粗、居中、单倍行距，尽量单行 |
| 一级标题 | “一、”中文编号，黑体、14 pt、加粗、居中 |
| 二/三级标题 | `2.1` 等，宋体、12 pt、加粗、左对齐 |
| 正文 | 宋体小四 12 pt，两端对齐，首行缩进 2 字符，1.5 倍行距，段前后 0 |
| 图表题 | 宋体 10.5 pt、居中、1.5 倍行距 |
| 参考文献/短附录 | 宋体 10.5 pt、1.25 倍行距，参考文献悬挂缩进 |
| 表内文字 | 宋体 10 pt、1.15 倍行距，垂直居中 |
| 显示公式 | 原生 OMML、居中；不把纯数字算式独立成段 |
| 引文 | 正文 `[n]` 上标；文末编号基线显示 |

版式实现原则：

- 只把题名、一级标题、图片、图题和表题居中；普通正文两端对齐，次级标题左对齐。
- 文档网格 `linePitch=360`，同时禁用段落对网格的异常吸附，避免含行内公式的行距被额外撑高。
- 题名若多一两个字，先精炼标题；需要保留术语时可在模板允许范围内缩到 15 pt，不通过强制窄缩字符解决。
- 表题与表头绑定，避免孤立表头；允许长表自然跨页，但不允许一个步骤行被切得只剩一两个字。
- PDF 仅作为临时渲染/逐页 QA，不是用户交付物，也不进入仓库。

## 7. 公式与表格规范

### 公式

- 变量定义和非平凡模型关系可显示；`140/12`、百分比换算等纯数字计算写在正文。
- 复合下标写成同一层：`d_{ij}`、`T_{ea}`；转换后检查 OMML 脚本区是单一 run。
- 裸星号写为 `D^{\ast}`，避免 Markdown 把 `*` 当强调标记。
- 使用标准数学写法：余数 `%`，指数函数 `\exp(\cdot)` 或 `e^{\cdot}`。
- 公式出现“空白/竖排/缺字”时检查转换后的 OOXML，不只看 Markdown 源码。

### Pandoc Markdown单一正文源

- 每版只维护`A题论文(vX.Y).md`这一份Markdown，作为可编辑正文与DOCX转换的权威源。
- 使用`$...$`、`$$...$$`、`^\[n\]^`和`{width=N%}`，优先保证Pandoc到Word的转换稳定性。
- 不再发布派生GitHub预览文件，也不为GitHub渲染器维护第二套数学、引文或图片宽度语法。
- Word排版特例同步进后处理脚本和测试；任何内容变更均先回到Pandoc源并经用户审核。

### 三线表

- 用户在 Word/WPS 中定稿的表格优先级高于通用表格规则。后续版本若表格内容未变，整表继承人工版的完整 OOXML（列宽、段落对齐、字号、换行、边框、单元格边距、行属性和表样式），不再按通用规则重算；若内容变化则停止继承并要求重新排版，禁止静默覆盖。
- 人工表格基线必须记录路径和 SHA-256；回归测试对比完整表格布局，并用渲染页复核独字行、混合对齐和意外换行。
- 只有顶线、表头下线、底线；无竖线、左右线和内部网格。
- 顶/底线 1.25 pt（OOXML `w:sz=10`），表头线 0.5 pt（`w:sz=4`）。
- 表内 10 pt；短字段尽量单行。列宽按语义分配，不机械等分。
- 算法表表头居中，正文第一列“Step”与第二列说明均左对齐。
- 结果表按列统一：文本说明左对齐，方案/数值列居中或小数点对齐。
- 优先调列宽、边距和措辞，再考虑缩字号；10 pt 与单行通常不冲突。

## 8. 科研图表规范

### 8.1 图表契约

每张正式图在绘制前填写：

```text
核心结论：读者看完只能得到什么主要结论？
数据来源：哪个结果文件、哪些列、单位、样本量？
图型：为什么该图型比表格/其他图更合适？
面板：每个面板承担哪条证据，哪个是主面板？
不确定性：SD/SEM/95% CI/无，n是多少？
最终尺寸：插入Word后的实际宽高与最小字号。
替代方案：黑白打印或颜色不可见时如何识别？
```

### 8.2 选图与信息密度

- 空间位置与联系：地图/网络图。
- 长期分流组成：水平堆叠条形图，段内标精确量；比大矩阵更直观。
- 策略多指标：一张非等权多面板图，主指标面积更大；不做雷达图。
- 连续参数与置信带：折线/响应曲线加 95% 带。
- 多节点精确置信区间：表格保留数值，配一张成对差森林图/点区间图。
- 绝对曲线重合但差异重要：不要误称绘图错误；增加差值图和置信区间。
- 同一证据不同时用表、热力图和柱状图重复三遍。

### 8.3 视觉基线

- 按最终 Word 尺寸直接出图，不插入后大幅缩放。
- 折线、散点、柱、热力图同时输出 SVG 和 300 dpi PNG；不用 JPEG。
- 使用色盲友好配色，并用线型/点型做冗余编码；生成灰度预览。
- 图内中文字体与论文协调；标签/刻度一般 7—9 pt，最小不低于 6 pt。
- 标题简短，详细统计口径放图注；图注说明 CI 类型、n、共同随机数或检验方法。
- 交付前检查彩色图、灰度图和 Word 实际插入尺寸，防止遮挡、裁切、图例压缩和小字。

## 9. 写作语体检查

需要重点替换的表达：

- “没有意义”“真正需要优化的是” → 客观写出分析顺序和决策变量。
- “不能声称”“不予虚构”“不把它解释为” → 直接界定数据来源、指标包含项和适用边界。
- “这样比较的正是……” → 写明共同随机数/对照实验的统计对象。
- “不能任意加权” → 说明量纲、归一化尺度和偏好系数问题，再给出词典序或 ε 约束理由。
- “显然”“不难发现”“值得注意” → 删除或换成数据/定理/约束证据。

学术化修改不得改变数字、模型名、结论方向、表号或引文事实。先做事实盘点，再改写，最后逐项核验。

## 10. 终审与发布清单

### 内容冻结

- [ ] 每问均有“问题—方法—结果—验证—边界”。
- [ ] 摘要数字全部能回到结果文件和正文。
- [ ] 数据字段都有“使用/不使用及原因”。
- [ ] 方案差异、显著性与因果边界没有夸大。
- [ ] 决策日志中的冻结项与论文一致。

### Word 冻结

- [ ] 题名单行，一级标题中文编号。
- [ ] 正文宋体小四、1.5 倍、两端对齐；无意外居中。
- [ ] 显示公式全部居中，复合下标横排完整。
- [ ] 引文上标，图表编号连续、正文均引用。
- [ ] 三线表无行级粗边框；列宽、字号和对齐统一。
- [ ] 逐页无裁切、重叠、孤立表头、孤字续页和不必要大片空白。

### Git/Release

- [ ] 新版本目录只包含Pandoc源MD、DOCX和转换清单，不生成派生预览MD。
- [ ] 中英文 README 同步增加发行说明，时间精确到分钟并使用 UTC+8。
- [ ] 论文发行时间只绑定正式论文交付物；预览、生成器、测试或模板更新写入独立的工作流与模板更新记录，不改写论文发行时间。
- [ ] 只显式暂存本项目路径，不包含其他任务的 `shared/` 文件。
- [ ] 提交作者为用户 GitHub 身份。
- [ ] 新版 DOCX 挂到对应 Release；下载资产与正式文件一致。
- [ ] 最终哈希只计算一次；推送后只核对一次远端提交与 Release。

## 11. 版本规则

- 拼写、少量排版、图表微调：递增次版本，如 v2.3 → v2.4。
- 模型合同、主要算法、核心结果或论文结构大改：升级主版本，如 v2.x → v3。
- 已发布版本不原地覆盖；若 Release 附件需修复，README 标明“首次发布”和“更新时间”。
- 每个版本均写清“改了什么、没改什么、为何改、验证状态”。

## 12. 优质规则自动沉淀机制

用户已授权助手把后续发现的优质规则主动加入本工作流。自动沉淀必须同时满足以下条件：

1. 已在真实论文、官方渲染器或可复现测试中验证，而不是仅凭经验判断；
2. 能跨题目复用，不是针对某一段文字、某一张表或某次软件异常的一次性补丁；
3. 不与当届官方规范、当前模板和用户已经冻结的决定冲突；
4. 能说明适用范围、反例或失效条件；
5. 能自动检查的规则同步写入`personal-paper-profile.yaml`，流程性规则写入本文件；同时记录来源和日期。

以下情况不得自动提升为长期规则：尚未验证的猜测、单个软件版本的偶发现象、为了绕过错误而形成的临时命令、会改变模型口径或论文结论的做法。若新规则将显著改变现有工作流或与既有规则冲突，必须先向用户确认，而不是自行覆盖。

本机制首次记录：2026-08-13，曾基于v2.4的GitHub渲染兼容问题形成双目标预览规则；同日用户明确改回Pandoc单一正文源，因此该规则已废止，不再复用。

第二条记录：2026-08-13，来源为v2.4配套预览和模板更新曾误改论文发行时间；经正式DOCX未变化、Git提交时间线和Release边界核对后，形成“论文发行日志与工作流/模板日志分离”的规则。
